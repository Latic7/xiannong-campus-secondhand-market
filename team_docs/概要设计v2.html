一引言

1.1 编写目的

本文档为《校园二手交易平台》的概要设计报告，依据需求分析结果，对系统的宏观结构、模块划分、核心数据模型、接口风格、关键流程、非功能策略、部署环境和后续详细设计计划进行说明。

概要设计只回答“系统由几部分构成、各部分如何协作、数据核心关系是什么”，不展开字段级数据库设计、接口参数明细、类图或伪代码。

本文档的作用是给后续详细设计和实现阶段提供统一蓝图，保证前端页面组织、后端服务边界、数据关系和流程状态在同一套设计语义下展开。

边界说明：若后续需要详细设计，可在此基础上继续展开数据库物理表、完整接口文档、状态机详表和类图。

1.2 文档范围

本报告覆盖系统整体架构、模块划分、概念数据模型、接口约定、关键流程、非功能策略、部署环境以及后续详细设计规划，重点在于形成“从需求到实现”的过渡性设计说明。

报告内容面向课程作业场景进行组织，因此既保留足够的工程化表达，也避免进入字段级、代码级和脚本级的详细实现层面。

1.3 术语与约定

  • “普通用户”指完成微信登录并注册的在校学生，统一承担买卖两类行为。
  • “管理员”指平台运营和审核人员，拥有内容审核和违规处理权限。
  • “在售、保留中、交易中、已完成、已取消”用于描述商品或订单的主流程状态。
  • 文中出现的模块名称和流程名称，均按系统宏观职责划分理解，不对应具体类名。

二系统总体架构

2.1 架构风格

系统采用前后端分离的分层架构：微信小程序负责页面与交互，FastAPI 负责业务编排与接口输出，MySQL 承载持久化数据，Redis 和对象存储承担缓存与资源存储，微信开放平台提供身份认证能力。

从实现视角看，前端只负责“展示、提交、反馈”，后端负责“鉴权、校验、流程控制、数据读写”，中间通过标准化 JSON 接口通信，便于分工和后续扩展。

flowchart LR U[微信小程序前端] -->|HTTPS / JSON| N[Nginx 反向代理] N --> A[FastAPI 应用服务] A --> M[业务模块层] M --> AU[账号与认证] M --> UM[用户与管理] M --> PM[商品与审核] M --> TM[交易与评价] M --> RM[举报与投诉] M --> SM[统计与运维] AU --> D[(MySQL)] UM --> D PM --> D TM --> D RM --> D SM --> D A --> R[(Redis 缓存)] A --> O[(对象存储)] A --> W[微信开放平台]

从整体上看，系统的边界非常清晰：用户访问链路从微信小程序开始，经由 Nginx 转发进入后端服务，再由后端服务访问数据库和外部资源。这样可以让前端、后端和数据层彼此独立演进，降低耦合。

在运行方式上，系统更接近“轻客户端 + 业务中台”的组合形态。前端承担较少的业务判断，复杂的审核、状态切换和权限控制统一收敛到后端处理，从而保证规则一致性和数据可靠性。

职责说明：前端只负责展示与交互，后端只负责业务规则和数据访问；接口通信采用 HTTPS 和 JSON，不在本阶段定义具体端口和路径实现细节。Redis 主要用于热点商品、验证码或临时状态缓存，对象存储主要用于商品图片、头像等静态资源。

2.2 分层职责

层次职责通信方式
客户端层首页浏览、商品发布、交易处理、个人中心、后台入口HTTPS / JSON
接口层统一鉴权、参数校验、响应封装、版本控制RESTful API
业务层用户、商品、交易、审核、举报、收藏、统计服务间方法调用
数据层MySQL 持久化、Redis 缓存、对象存储ORM / 缓存读写

架构补充：接口层统一处理登录态、异常码和参数校验，业务层按“账号、用户、商品、交易、举报、统计”拆分职责，减少跨模块直接访问数据库的情况。收藏功能归属于“用户与管理”模块下的个人中心子功能，无需独立模块。

这种分层方式的直接好处，是可以将展示问题、业务问题和数据问题分离处理。例如，页面跳转和交互属于前端职责，交易是否成立、商品是否可售属于业务职责，而数据一致性和历史记录留存则由持久化层负责。

同时，外部依赖被控制在最外层，微信登录和对象存储都通过标准接口接入，不会影响核心业务模块的设计稳定性。后续如果增加支付、消息通知或校园认证，也可以沿着同样的分层边界扩展。

模块划分采用“按业务能力切片”的方式组织，而不是按页面或按钮进行简单拆分。这样做的目的，是确保每个模块都能围绕一个明确目标独立演进，并在接口层面形成稳定边界。

在课程作业场景下，这种划分也更便于后续分工：账号认证、商品发布、交易确认、举报处理、后台审核和统计分析可以分别展开，既能体现系统完整性，也便于在后续详细设计中逐项补充。

设计说明：收藏功能归属于“用户与管理”模块的个人中心子功能，无需独立模块。举报与投诉独立成模块，因其涉及管理员审核流程和后续处理，与普通收藏行为性质不同。

四概念数据模型

4.1 核心实体

概念模型仅保留实体和关系：用户、管理员、商品、商品图片、商品类别、交易订单、收藏、评价、举报、管理员日志和统计汇总。用户统一建模，不单独拆分“买家账号”和“卖家账号”。

其中，商品是业务主对象，交易是流程主对象，评价和举报是治理主对象，统计汇总则服务于运营分析与后续优化决策。

erDiagram USER ||--o{ PRODUCT : publishes CATEGORY ||--o{ PRODUCT : classifies PRODUCT ||--o{ PRODUCT_IMAGE : has USER ||--o{ TRADE_ORDER : buys USER ||--o{ TRADE_ORDER : sells PRODUCT ||--o{ TRADE_ORDER : relates_to USER ||--o{ FAVORITE : creates PRODUCT ||--o{ FAVORITE : collected_by TRADE_ORDER ||--o{ REVIEW : produces USER ||--o{ REVIEW : writes USER ||--o{ REPORT : submits USER ||--o{ ADMIN_LOG : operates

从概念层看，商品、交易和评价构成了平台最核心的业务闭环：商品为交易提供载体，交易为评价提供触发条件，评价又反过来影响用户信誉。这个闭环决定了系统的主要数据流向。

举报和管理员日志的加入，则体现出平台治理能力。它们不直接参与商品交易，但对平台安全、秩序维护和事后追踪非常重要，因此在概念模型中应当被明确表达。

关系类型说明
用户 - 商品1:N一个用户可发布多个商品
商品类别 - 商品1:N一个类别下包含多个商品
商品 - 图片1:N一件商品可对应多张图片

用户 - 交易 - 商品1:N / 1:N交易记录连接买家、卖家与商品

只到实体与关系级别，不出现字段、数据类型、主键外键等物理设计内容。举报和日志采用“对象类型 + 对象编号”的方式表达，便于统一管理商品举报和用户举报两类场景。

五接口设计原则

5.1 接口约定

  • 接口采用 RESTful 风格，统一以 /api/v1 作为版本前缀。
  • 身份认证采用微信登录 + JWT，管理员接口额外进行角色校验。
  • 统一返回结构只保留 code、message、data 三部分，避免不同模块返回风格不一致。
  • 接口只展示 URI、方法和用途，不展开完整请求和响应字段。

本阶段仅以普通用户核心接口为例说明规范。管理员审核、用户管理、举报处理、统计报表等接口遵循相同 RESTful 风格，具体路径、请求与响应字段在详细设计阶段定义。

示例接口方法简要说明
/api/v1/auth/wx-loginPOST微信登录并签发 Token
/api/v1/productsGET / POST获取商品列表或发布商品
/api/v1/orders/{id}/confirmPUT卖家确认交易请求

接口设计还应遵循“前端易调用、后端易维护”的原则。也就是说，路径命名尽量体现资源语义，返回值尽量保持稳定，避免同一接口在不同模块中出现不同的报文风格。

对于课程作业而言，示例接口足以说明系统的接口边界和调用方式；更细的字段级说明、分页参数和错误码定义可以留给详细设计阶段展开。

接口层的主要任务是统一鉴权、统一返回、统一版本，不负责具体数据表结构定义。这个阶段只给出接口骨架，详细参数、字段约束和示例报文放到后续详细设计。

六关键业务流程

6.1 商品发布与审核流程

该流程是平台最典型的主链路：用户先提交商品信息，管理员完成审核后，商品才进入可交易状态。这个设计能保证平台内容质量，也能降低违规商品直接上架的风险。

flowchart TD A[用户登录] --> B[填写商品信息] B --> C[上传图片] C --> D[提交审核] D --> E[管理员审核] E --> F{审核结果} F -->|通过| G[商品上架] F -->|拒绝| H[退回修改]

发布流程体现了平台对内容质量的前置把控。用户侧只负责录入商品信息和上传图片，审核判断统一交给管理员处理，这样可以避免普通用户直接暴露复杂的规则判断。

在流程设计上，“审核中”是重要的过渡态，它确保商品不会在内容未校验的情况下进入交易界面。对于课程设计来说，这种流程很适合展示平台治理能力和状态控制能力。

6.2 交易流转状态机

交易流程围绕“请求、确认、进行、完成、取消”五个阶段展开，保留超时取消机制，以避免商品长期处于保留状态而影响平台流转效率。

stateDiagram-v2 [*] --> 在售 在售 --> 保留中: 发起购买请求 保留中 --> 交易中: 卖家确认 保留中 --> 在售: 卖家拒绝/超时取消 交易中 --> 已完成: 双方确认完成 交易中 --> 在售: 交易取消 已完成 --> [*]

交易状态机的作用，是将线下交易过程转化为可追踪、可回放的系统状态。这样即使交易过程发生取消、超时或争议，也能够通过状态记录还原问题经过。

该状态机同时说明了系统的一个设计原则，即以“当前状态 + 状态变更事件”来组织交易逻辑，而不是让前端自行推断交易是否完成。这样有助于保证订单一致性和业务可控性。

6.3 举报与投诉处理流程

用户对商品或用户发起举报后，举报进入待处理队列；管理员在后台审核，可做出“驳回”、“警告被举报人”、“下架商品（商品举报）”或“封禁用户”等处理，处理结果通知举报人。

时序图和状态机只展示主要参与对象及状态流转，不展开异常分支的代码级处理逻辑。

七非功能与部署

7.1 非功能需求实现策略

性能

分页查询、Redis 缓存、商品封面图压缩、统计结果预聚合。

安全

HTTPS、JWT、后台角色校验、联系方式脱敏、上传文件校验。

可用性

统一错误提示、超时任务扫描、关键操作日志和状态回滚。

可维护性

前后端分离、模块化代码组织、接口分层、日志与监控预留。

非功能维度策略目的
性能缓存热点数据、分页加载、资源压缩缩短首屏和搜索响应时间
安全鉴权、权限、脱敏、上传限制、日志审计降低越权与泄露风险
可用性统一错误处理、超时任务、状态回滚提升业务连续性
可维护性模块化、接口分层、配置外置方便扩展与后期修改

7.2 部署与运行环境

系统建议以云服务器或校内服务器方式部署，后端服务与数据库分离，静态资源可放在对象存储或独立文件目录中。这样既方便课程演示，也便于后续上线扩容。

flowchart LR C[微信客户端] --> P[微信小程序] P --> N[Nginx / HTTPS] N --> S[FastAPI 服务] S --> M[(MySQL 8.0)] S --> R[(Redis)] S --> O[(对象存储)] S --> W[微信开放平台]

部署拓扑尽量保持简洁，核心思路是将入口、应用、数据和资源存储分开部署。这样不仅便于后期扩容和维护，也能在出现问题时快速定位故障所在层级。

对于课程作业展示，这种部署方式足以体现现代 Web 应用的基本运行形态：用户请求先经过反向代理，再进入应用服务，最后访问数据库或外部资源，层次分明且易于理解。

组件建议作用
操作系统Windows / Linux承载后端与中间件
Web 入口Nginx反向代理与 HTTPS
应用服务Python 3.11 + FastAPI业务接口与流程编排
数据库MySQL 8.0持久化核心业务数据
缓存Redis热点数据和短期状态
静态资源对象存储或本地文件商品图片与附件
