一引言

1.1 编写目的

本文档为《校园二手交易平台》的概要设计报告，依据需求分析结果，对系统的宏观结构、模块划分、核心数据模型、接口风格、关键流程、非功能策略、部署环境和后续详细设计计划进行说明。

文档重点在于业务流程的模块化设计：将系统拆分为账号与认证、用户与管理、商品与审核、交易与评价、举报与投诉、统计与运维等关键模块，并定义模块级接口边界与协作关系。

本文档的作用是给后续详细设计和实现阶段提供统一蓝图，保证前端页面组织、后端服务边界、数据关系和流程状态在同一套设计语义下展开。

1.2 文档范围

本报告覆盖系统整体架构、模块划分、概念数据模型、接口约定、关键流程、非功能策略、部署环境以及后续详细设计规划，重点在于形成“从需求到实现”的过渡性设计说明。

1.3 术语与约定

  • “普通用户”指完成微信登录并注册的在校学生，统一承担买卖两类行为。
  • “管理员”指平台运营和审核人员，拥有内容审核和违规处理权限。
  • “在售、保留中、交易中、已完成、已取消”用于描述商品或订单的主流程状态。

二系统总体架构

2.1 架构风格

系统采用前后端分离的分层架构：微信小程序负责页面与交互，FastAPI 负责业务编排与接口输出，MySQL 承载持久化数据，微信开放平台提供身份认证能力；Redis、对象存储作为可选增强项用于提升性能和资源管理能力。

从实现视角看，前端只负责“展示、提交、反馈”，后端负责“鉴权、校验、流程控制、数据读写”，中间通过标准化 JSON 接口通信，便于分工和后续扩展。

flowchart LR U[微信小程序前端] -->|HTTPS / JSON| A[FastAPI 应用服务] A --> M[业务模块层] M --> AU[账号与认证] M --> UM[用户与管理] M --> PM[商品与审核] M --> TM[交易与评价] M --> RM[举报与投诉] M --> SM[统计与运维] AU --> D[(MySQL)] UM --> D PM --> D TM --> D RM --> D SM --> D A --> R[(Redis 缓存（可选）)] A --> O[(对象存储（可选）)] A --> W[微信开放平台]

从整体上看，系统的边界非常清晰：用户访问链路从微信小程序开始，直接进入后端服务，再由后端服务访问数据库和外部资源。这样可以让前端、后端和数据层彼此独立演进，降低耦合。

在运行方式上，系统更接近“轻客户端 + 业务中台”的组合形态。前端承担较少的业务判断，复杂的审核、状态切换和权限控制统一收敛到后端处理，从而保证规则一致性和数据可靠性。

职责说明：前端只负责展示与交互，后端只负责业务规则和数据访问；接口通信采用 HTTPS 和 JSON。Redis 与对象存储属于可选增强项，分别用于热点缓存和静态资源管理，通过后续进行技术测试，证明它们易用且符合要求后，再考虑使用它们。

2.2 分层职责

层次职责通信方式
客户端层首页浏览、商品发布、交易处理、个人中心、后台入口HTTPS / JSON
接口层统一鉴权、参数校验、响应封装、版本控制RESTful API
业务层用户、商品、交易、审核、举报、收藏、统计服务间方法调用
数据层MySQL 持久化（核心）+ Redis 缓存（可选）+ 对象存储（可选）ORM / 缓存读写
外部依赖微信登录、图片存储、消息通知预留开放平台接口
架构补充：接口层统一处理登录态、异常码和参数校验，业务层按“账号、用户、商品、交易、举报、统计”拆分职责，减少跨模块直接访问数据库的情况。收藏功能归属于“用户与管理”模块下的个人中心子功能，无需独立模块。

这种分层方式的直接好处，是可以将展示问题、业务问题和数据问题分离处理。例如，页面跳转和交互属于前端职责，交易是否成立、商品是否可售属于业务职责，而数据一致性和历史记录留存则由持久化层负责。

同时，外部依赖被控制在最外层，微信登录和对象存储都通过标准接口接入，不会影响核心业务模块的设计稳定性。后续如果增加支付、消息通知或校园认证，也可以沿着同样的分层边界扩展。

三模块划分与职责

3.1 核心模块

账号与认证

负责微信登录、首次注册、Token 签发与注销。

用户与管理

负责普通用户资料、信誉分、封禁解封和收藏管理。

商品与审核

负责商品发布、编辑、上下架、审核与图片管理。

交易与评价

负责购买请求、确认、完成、取消、评价与信誉联动。

举报与投诉

负责用户举报提交、举报处理、投诉跟踪与状态反馈。

统计与运维

负责运营统计、管理员后台、日志与可观测性。

模块划分采用“按业务能力切片”的方式组织，而不是按页面或按钮进行简单拆分。这样做的目的，是确保每个模块都能围绕一个明确目标独立演进，并在接口层面形成稳定边界。

设计说明：收藏功能归属于“用户与管理”模块的个人中心子功能，无需独立模块。举报与投诉独立成模块，因其涉及管理员审核流程和后续处理，与普通收藏行为性质不同。

从概念层看，商品、交易和评价构成了平台最核心的业务闭环：商品为交易提供载体，交易为评价提供触发条件，评价又反过来影响用户信誉。这个闭环决定了系统的主要数据流向。

举报和管理员日志的加入，则体现出平台治理能力。它们不直接参与商品交易，但对平台安全、秩序维护和事后追踪非常重要，因此在概念模型中应当被明确表达。

五接口设计原则

5.1 全局接口约定

  • 接口采用 RESTful 风格，统一以 /api 作为基础路径，模块按资源语义命名。
  • 身份认证采用微信登录 + JWT，管理员接口基于角色权限进行二次校验。
  • 统一响应结构为 code / message / data / requestId / timestamp，便于前后端联调与问题追踪。
  • 列表查询统一支持分页与筛选参数（page、size、keyword、sort），降低接口差异化成本。
约定项统一规范说明
基础路径/api保持路径稳定，版本通过发布流程管理
鉴权方式Bearer JWT普通用户与管理员采用同一令牌体系，权限分层控制
时间格式ISO 8601统一时区表达，便于日志与数据库比对
错误码业务码 + HTTP 状态码客户端可读、服务端可追踪

/api/admin/stats/tradesGET获取交易维度统计数据交易与评价、商品与审核

本节给出的是概要阶段的接口边界与命名约定，字段级请求参数、响应示例与错误码明细在详细设计阶段单独落地。

六非功能与部署

6.1 非功能需求实现策略

性能

分页查询、Redis 缓存、商品封面图压缩、统计结果预聚合。

安全

HTTPS、JWT、后台角色校验、联系方式脱敏、上传文件校验。

可用性

统一错误提示、超时任务扫描、关键操作日志和状态回滚。

可维护性

前后端分离、模块化代码组织、接口分层、日志与监控预留。

非功能维度策略目的
性能缓存热点数据、分页加载、资源压缩缩短首屏和搜索响应时间
安全鉴权、权限、脱敏、上传限制、日志审计降低越权与泄露风险
可用性统一错误处理、超时任务、状态回滚提升业务连续性
可维护性模块化、接口分层、配置外置方便扩展与后期修改

6.2 部署与运行环境

系统计划以微信“云托管”的方式部署，后端服务与数据库分离；Redis、对象存储作为可选增强项，可在后续性能和运维需求明确后按需引入。静态资源也可先采用本地文件目录方案。

flowchart LR C[微信客户端] --> P[微信小程序] P --> S[FastAPI 服务] S --> M[(MySQL 8.0)] S --> R[(Redis（可选）)] S --> O[(对象存储（可选）)] S --> W[微信开放平台]

部署拓扑尽量保持简洁，核心思路是将入口、应用、数据和资源存储分开部署。Redis、对象存储通过后续进行技术测试，证明它们易用且符合要求后，再考虑使用它们。

七后续详细设计计划

7.1 概览与目标

本节给出面向实现的详细设计交付清单与每个核心模块的设计要点，内容覆盖字段级接口契约、主要物理表草图与索引建议、关键算法/状态机、缓存策略、异常处理与重试、测试覆盖与迁移要点。目标是在二周内产出可直接交付给开发与测试的设计文档与示例实现。

7.2 交付清单（产物）

  • 模块级 API 文档（每个接口的请求/响应字段、示例、错误码、权限）
  • 数据库物理表草图（主键、外键、重要索引、常用查询分析）
  • 关键流程状态机与伪代码（订单、审核、举报处理）
  • 缓存与一致性策略说明（哪些数据缓存、TTL、失效策略）
  • 异常/重试策略与运维检查清单
  • 测试计划（单元、集成、端到端、对接微信平台的模拟方案）
  • 迁移与回滚要点（DDL 变更策略、数据补齐脚本）

7.3 按核心模块的详细设计要点（只是草案！）

账号与认证

  • 接口示例：/api/auth/wx-login（POST）请求字段：{code:string, clientId?:string}；响应字段：{code:0,message:'ok',data:{accessToken,refreshToken,expiresIn,user:{id,wxOpenId}}}。
  • DB 草图：表 users（id PK, wx_openid UNIQUE, nickname, avatar, status, created_at, updated_at），在 wx_openid 上建立唯一索引。
  • 安全与会话：JWT 包含 user_id、roles、iat、exp；短期 access token（默认 1 小时），refresh token 用于续期；必要时在 Redis 中维护黑名单以实现强制下线（可选）。
  • 异常处理：微信授权失败返回明确业务码；对外请求（微信 API）采用指数退避 + 最多 3 次重试，失败记录到告警系统并返回 502 给客户端。

用户与管理

  • 接口字段级示例：/api/users/me GET 返回用户详情，包含信誉分 score 与封禁状态 status。
  • DB 草图：表 user_profile（user_id FK, college, contact_masked, score INT, banned_until DATETIME NULL），为 score 建立索引以支持排行和过滤。
  • 缓存策略：个人资料读多写少，建议缓存用户基本信息（TTL 300s），写入时触发缓存失效或更新。
  • 管理员操作需记录 admin_logs 表（actor_id, target_type, target_id, action, remark, created_at）。

商品与审核

  • 接口规范：发布接口要求字段校验（title, price, category_id, images[]），图片先上传到对象存储后回传 URL；审核相关接口仅管理员可调用。
  • DB 草图：表 products（id PK, owner_id FK, title, description, price, status ENUM('draft','pending','published','removed'), category_id, created_at, updated_at），对 status 与 owner_id 建复合索引以加速待审与用户列表查询。
  • 审核队列：采用 product_reviews 表保存审核记录（product_id FK, reviewer_id, result, reason, processed_at），管理员处理时通过事务更新 products.status 与插入审核记录。
  • 图片处理：建议客户端限制尺寸/压缩，在服务端再做校验；对象存储按日期分层，URL 使用带签名的短期访问策略（如果支持）。

交易与评价

  • 订单状态机（核心）：CREATED -> RESERVED -> CONFIRMED -> COMPLETED | CANCELLED。关键事件：buyer_request、seller_confirm、complete、cancel、timeout。
  • DB 草图：表 orders（id, product_id FK, buyer_id, seller_id, amount, status ENUM, created_at, expire_at），为 status 与 buyer_id 建索引。
  • 并发控制：下单时使用悲观/乐观策略之一（推荐在业务层用数据库事务 + 状态条件更新，如 UPDATE ... WHERE status='published' 返回受影响行数判断成功）。
  • 补偿与超时：设置保留超时时间（例如 15 分钟），通过定时任务扫描过期订单并自动释放商品，记录回退日志。

举报与投诉

  • 处理流程：用户提交举报入库（reports），管理员在后台查看并处理（驳回/警告/下架/封禁），处理结果写入处理日志并通知用户。
  • DB 草图：reports（id, reporter_id, target_type, target_id, reason, status ENUM('open','rejected','handled'), assignee_id, created_at, handled_at）。
  • 优先级与报警：对于重复举报或高严重度（如欺诈）自动标记高优先级并通知值班管理员。

统计与运维

  • 统计数据：对在线统计需求采用定时聚合（每日/每小时）写入统计结果库，避免对主业务库做重查询。
  • 可观测性：接入日志聚合、错误报警、关键业务指标（下单率、通过率、审核时延）并建立仪表盘。

7.4 公共设计约定

  • 统一错误码：采用业务码前缀（例如 1000–1999 为认证/用户类，2000–2999 为商品类），并映射标准 HTTP 状态码。
  • 事务边界：每个接口应尽量保持单一事务边界，跨模块变更通过事件/补偿机制处理，避免长事务。
  • 外部 API 调用：对微信等外部服务实行幂等重试（最多 3 次，指数退避），对关键步骤增加可人工介入的异常单记录。
  • 性能指标：关键接口 95p 响应 < 500ms（不包含图片上传），数据库查询避免全表扫描，加入必要索引并监控慢查询。

7.5 测试与验收

  • 单元测试覆盖核心业务逻辑（订单状态变迁、审核规则），接口层做契约测试。
  • 集成测试包含：MySQL + FastAPI 的全链路测试；对接微信登录接口使用模拟/回放（mock server 或微信 sandbox）。
  • 验收标准：主链路（登录、发布、浏览、下单、完成）通过端到端验收用例；关键运维指标达标且无致命错误。

7.6 部署、迁移与回滚要点

  • DDL 变更：采用灰度发布与版本迁移脚本（先做兼容字段，再后台迁移，最后删除旧字段），并在变更前后运行一致性检查脚本。
  • 回滚策略：回滚仅限于可逆变更（应用回滚 + 配置回退），不可逆数据迁移需准备补偿脚本。

7.7 优先级与交付顺序

  1. 账号与认证、用户资料、商品发布与浏览（确保主链路可用）
  2. 交易流程（订单创建、确认、完成、取消、超时处理）
  3. 商品审核与后台管理（审核队列、日志）
  4. 举报处理与申诉流程
  5. 统计与运维、缓存与优化（根据实际负载选择 Redis/对象存储）
