# 开工前约定清单

本文档用于在正式开发前统一项目规则，目的不是补全所有占位代码，而是先把后续最容易扯皮、最容易返工的约定定下来。

适用范围：校园二手交易平台微信小程序项目的前端、后端、数据库、测试与联调流程。

## 1. 必须先确认的规则

### 1.1 权限边界

必须明确“谁能看、谁能改、谁能删、谁能审核”。至少要先定以下内容：

- 普通用户只能修改**自己**的资料、商品和订单相关信息。
- 卖家只能操作**自己**发布的商品和自己相关的订单。
- 买家只能操作**自己**发起的订单和自己的评价。
- 管理员拥有封禁用户、下架商品、处理举报、查看统计的权限。
- 用户被封禁后，依然**能够**查看历史订单、提交举报、访问商品列表。

### 1.2 状态机规则

必须先定义状态流转，而不是开发时随手写状态字段。至少包括：

- 商品状态：草稿、待审核、已发布、已下架、已售出。
- 订单状态：已创建、已保留、已确认、已完成、已取消。
- 举报状态：未处理、已驳回、已处理。
- 用户状态：正常、封禁。

同时要明确：

- 哪些状态可以前进，哪些状态不允许回退。
- 哪些动作在什么状态下允许，什么状态下禁止。
- 状态变更是否需要记录操作日志。

状态机中的状态应该以**枚举类**的形式统一放在后端的 [server/app/core/status.py](../server/app/core/status.py) 中集中维护，后端业务代码、数据库迁移脚本和 OpenAPI 草案都以这份定义为准。前端如果需要展示中文文案或颜色，也应当只做显示层映射，不要自己重新发明一套状态值。

### 1.3 数据归属规则

必须先说明哪些字段由谁维护，避免前后端和数据库同时改同一份数据。

优先确认：

- 用户如果是通过非微信方式注册的，则该用户的昵称、头像、联系方式由平台维护。如果是通过微信注册的，则应仅同步微信中的信息而不允许进一步修改。
- 商品价格在发布后允许修改，修改后无需重新审核。不过，如果有对该商品的订单出现，则锁定价格，不允许修改，以免发起订单的买家蒙受损失。
- 订单金额在下单后保持锁定，不允许后续变化。
- 举报处理结果不允许再次修改，只能通过申诉去覆盖原结果。

### 1.4 接口契约规则

接口草案已经写在 [docs/api/openapi-draft.yaml](api/openapi-draft.yaml)，但还需要补以下约定：

- 哪些字段是必填字段。
- 哪些字段允许为空。
- 哪些字段一旦确定就不能随便改名。
- 哪些字段可以新增，但不能改变旧字段语义。

### 1.5 错误处理规则

必须统一失败场景的返回方式，至少要先约定：

- 登录失败怎么返回。
- 权限不足怎么返回。
- 资源不存在怎么返回。
- 状态不允许怎么返回。
- 重复提交怎么返回。

如果前后端对失败语义理解不一致，后面联调时会非常痛苦。

异常类的设计不需要完全照搬 SpringBoot 的“每种细碎报错一个类”，但也不能所有错误都直接 `raise Exception`。建议采用“少量基础异常类 + 业务子类”的方式统一管理：

- 在后端的 [server/app/core/exceptions.py](../server/app/core/exceptions.py) 中集中定义基础异常类和常见业务异常类。
- 至少区分登录失败、权限不足、资源不存在、状态不允许、重复提交这几类高频场景。
- 每个异常类都应该携带统一的错误码、HTTP 状态码和默认错误信息。
- 路由层只负责抛异常，不要在每个接口里手写一套返回结构。
- 全局异常处理器负责把业务异常转换成统一响应格式，前端只根据错误码和 message 判断展示逻辑。

第一版推荐的粒度是“按业务语义分类”，不是“按每一句提示文案分类”。也就是说，像“未登录”“token 过期”“权限不足”“商品状态不允许”“重复提交订单”这种属于不同处理语义的情况，可以分别建类；但同一类下的细微提示差异，优先通过错误码和 message 参数表达，不必再额外拆出新异常类。

### 1.6 幂等和重复提交规则

必须明确这些操作是否允许重复执行，以及重复后如何处理：

- 收藏同一个商品。
- 重复提交订单。
- 重复提交举报。
- 重复审核同一商品。
- 重复完成同一个订单。

建议原则：对外可重复点击的动作，后端要么幂等返回成功，要么明确提示重复操作，不能产生重复脏数据。

### 1.7 数据库与命名规则

数据库负责人要先统一命名与约束，包括：

- 主键、外键、唯一索引、常用索引的命名方式。
- 状态字段的枚举值。
- 时间字段的格式和时区。
- 迁移脚本的命名方式。
- 数据库用户权限的范围。

建议结合 [docs/第一阶段任务分配表.md](第一阶段任务分配表.md) 一起确认。

### 1.8 分支和合并规则

必须先定好分支流转方式，避免后面代码混乱：

- 每个人是否都在自己的 feature 分支开发。
- 代码是先合到 dev 还是 test。
- 哪些改动必须先联调再合并。
- 谁负责最后的合并确认。

## 2. 推荐先定下来的 10 条结论

下面这 10 条建议作为第一版项目约定，正式开发前先在组会上确认：

1. 普通用户只能改自己的资料、收藏、商品和订单相关内容。
2. 管理员拥有审核、封禁、下架、统计查询权限，但所有操作都要留痕。
3. 商品状态以“草稿 -> 待审核 -> 已发布 -> 已下架/已售出”为主线。
4. 订单状态以“已创建 -> 已保留 -> 已确认 -> 已完成/已取消”为主线。
5. 举报状态以“未处理 -> 已驳回/已处理”为主线。
6. 订单完成、商品下架、举报处理都不能随意回退，必须有明确规则。
7. 收藏、下单、举报、审核都要考虑重复提交的处理方式。
8. OpenAPI 是字段契约的主依据，接口名和字段名不要随意改。
9. 数据库表命名、状态命名、时间字段命名要统一，不能各模块各写一套。
10. 代码先在 feature 分支开发，稳定后再合并到测试分支进行联调和验收。

## 3. 备注

如果后续在开发过程中发现规则需要调整，优先改这份文档，再同步更新 OpenAPI、任务分配表和数据库设计文档，避免不同文档之间互相打架。
