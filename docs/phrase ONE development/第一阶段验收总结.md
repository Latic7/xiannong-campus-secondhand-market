# 第一阶段验收总结

本文档基于当前仓库中已经提交的前后端代码、数据库草案、契约测试文件，以及 [docs/第一阶段任务分配表.md](../第一阶段任务分配表.md) 与 [docs/api/openapi-draft.yaml](../api/openapi-draft.yaml) 的要求，整理第一阶段开发计划的完成情况、与 OpenAPI 的一致性、以及后续需要补全和对齐的重点。

说明：本总结以静态代码检查和文档对照为依据，重点判断“是否已经落地”“是否能按约定联调”“是否与 OpenAPI 对齐”。它不是一次运行时验收报告，因此不会把“文件存在”直接等同于“功能完成”。

## 1. 总体结论

当前项目已经出现了可验收的骨架成果，但还没有达到第一阶段“主链路完整跑通”的标准。

从整体看，后端 A 的认证与用户资料链路、数据库 schema 草案、以及部分测试脚本是当前最接近可交付的内容；前端 A、前端 B、后端 B 主要仍处于“页面骨架 / 接口骨架 / mock 数据”的阶段，离真正的接口联调还有明显距离。

第一阶段最核心的目标是“前端能看到真实数据，后端能返回符合 OpenAPI 的字段，测试能把主流程和失败路径先检查一遍”。按照这个标准，当前状态更接近“起步阶段已完成一部分基础设施”，而不是“第一阶段完成版”。

## 2. 完成度判断

### 2.1 前端 A：主页和列表页

负责范围：

- [miniprogram/pages/home/index.js](../../miniprogram/pages/home/index.js)
- [miniprogram/pages/list/index.js](../../miniprogram/pages/list/index.js)
- [miniprogram/components/item-card](../../miniprogram/components/item-card)
- [miniprogram/utils/api.js](../../miniprogram/utils/api.js)

完成情况判断：**部分完成，偏骨架状态**。

已完成的内容：

- 首页和列表页都已经写出数据加载逻辑，页面不再是纯静态空壳。
- 首页已经尝试加载推荐商品和最新商品两块内容，也有分类入口和搜索入口。
- 列表页已经写出分页、关键词搜索、分类筛选、排序、价格区间筛选、下拉刷新和上拉加载更多的交互逻辑。
- `item-card` 组件已经能够展示标题、描述、价格和状态标签。

未完成或未真正接通的内容：

- [miniprogram/services/product.js](../../miniprogram/services/product.js) 仍是占位文件，没有真正实现请求。
- [miniprogram/utils/api.js](../../miniprogram/utils/api.js) 仍是占位实现，没有统一请求封装。
- 首页和列表页虽然在调用 `fetchProductList`，但实际服务层没有完成，无法形成真实数据链路。
- 列表页中还带有价格过滤、排序等前端逻辑，但后端 OpenAPI 草案并没有明确支持这些字段，属于“前端先写了 UI 能力，后端还没对齐”的状态。

结论：前端 A 已经完成了页面骨架和交互框架，但没有完成第一阶段要求的“从接口拿真实数据并展示”的目标。

### 2.2 前端 B：详情页、发布页和个人中心

负责范围：

- [miniprogram/pages/detail/index.js](../../miniprogram/pages/detail/index.js)
- [miniprogram/pages/post/index.js](../../miniprogram/pages/post/index.js)
- [miniprogram/pages/user/index.js](../../miniprogram/pages/user/index.js)
- [miniprogram/utils/storage.js](../../miniprogram/utils/storage.js)

完成情况判断：**部分完成，但核心链路仍是 mock**。

已完成的内容：

- 详情页已经有完整的页面结构、商品展示逻辑、收藏按钮、下单按钮、举报按钮和联系卖家入口。
- 发布页已经实现了表单结构、字段校验、图片选择/预览/删除的基础交互。
- 个人中心页已经具备登录态读取、本地缓存管理、退出登录、个人信息展示、收藏入口和发布入口。
- `utils/storage.js` 已经把 token、refresh token、过期时间和用户信息缓存统一收口，这一点符合“登录态先通过本地存储管理”的要求。

未完成或不符合预期的内容：

- 详情页并没有真正调用后端商品详情接口，而是直接使用 mock 商品数据。
- 个人中心页的登录逻辑是模拟写入本地存储，不是微信登录 + 后端 token 返回的真实链路。
- 个人中心页的统计数据也是 mock 值，不是从后端读取。
- 发布页虽然完成了表单与校验，但图片上传和商品发布提交仍是 TODO，没有接上后端接口。

结论：前端 B 完成了 UI 和交互层准备，但没有完成“根据商品 ID 拉取真实详情”“读取真实用户资料”“完成发布提交”的验收目标。

### 2.3 后端 A：认证与用户

负责范围：

- [server/app/api/routers/auth.py](../../server/app/api/routers/auth.py)
- [server/app/api/routers/users.py](../../server/app/api/routers/users.py)
- [server/app/schemas/common.py](../../server/app/schemas/common.py)
- [server/app/core/response.py](../../server/app/core/response.py)

完成情况判断：**相对最完整，接近可联调，但仍有对齐问题**。

已完成的内容：

- 微信登录、刷新 token、注销、当前用户查询这条链路已经有明确实现。
- 用户资料读取、资料更新、收藏列表、收藏新增、收藏删除这些接口都已经写出。
- 统一响应结构已经存在，返回字段包含 `code`、`message`、`data`、`requestId`、`timestamp`，这点与任务清单中的统一响应目标一致。
- `UserStatus`、`ProductStatus`、`OrderStatus`、`ReportStatus` 等状态枚举已经集中在后端状态文件中维护，方向是对的。

主要问题：

- 收藏列表接口返回的是收藏记录和 `productId`，不是 OpenAPI 中更偏向“商品收藏列表”的语义。
- `get_profile` 和 `get_current_user` 的返回字段目前比较接近，但仍需检查与 OpenAPI 的字段级约定是否完全一致，尤其是状态枚举值和前端展示字段。
- 登录链路强依赖微信真实接口和数据库中的 `User` 模型，当前更像“结构已搭好”，还需要补齐联调环境、测试数据和异常场景。

结论：后端 A 是当前第一阶段里最接近完成的一块，但仍有字段语义、返回结构和收藏接口语义需要继续对齐。

### 2.4 后端 B：商品与交易

负责范围：

- [server/app/api/routers/products.py](../../server/app/api/routers/products.py)
- [server/app/api/routers/orders.py](../../server/app/api/routers/orders.py)
- [server/app/schemas/common.py](../../server/app/schemas/common.py)

完成情况判断：**有路由，无完整实现，暂不能算完成**。

已完成的内容：

- 商品、订单相关路由已经挂出。
- 商品发布、商品详情、商品更新、商品删除、图片上传、图片删除、下单、确认、取消、完成、评价这些动作的接口路径都已经出现。

主要问题：

- 商品路由中直接调用了未定义的 `product_service`，说明业务服务层并没有真正落地。
- 订单路由中同样存在对未定义 `order_service` 的调用。
- 商品详情、商品列表、订单详情等接口目前大量返回硬编码或简化数据，不是基于真实持久化数据。
- 订单状态流转只是表面返回状态值，没有看到严格的状态机控制、权限校验和幂等处理。

结论：后端 B 目前只能算“接口壳子已写”，不能算第一阶段主链路完成。

### 2.5 后端 C：举报、后台与统计

负责范围：

- [server/app/api/routers/reports.py](../../server/app/api/routers/reports.py)
- [server/app/api/routers/admin.py](../../server/app/api/routers/admin.py)
- [server/app/schemas/common.py](../../server/app/schemas/common.py)

完成情况判断：**有基础路由和返回壳，但业务深度不足**。

已完成的内容：

- 举报提交、举报查询、申诉接口已经有基础实现。
- 后台用户列表、举报队列、商品待审核、审核动作、统计总览、统计序列、管理员日志接口都已经列出。

主要问题：

- 大部分接口返回的是固定空列表或固定统计值，没有真实后台数据支撑。
- 管理员用户管理接口虽然已经写出，但从任务分配表看，第一阶段其实只是“保留设计”，并不要求它成为硬性交付项。
- 举报与后台处理的状态流转、处理动作留痕、审批记录等关键业务闭环还未落地。

结论：后端 C 已经把接口面铺出来了，但仍属于“最小草案层”，离真正可验收的治理链路还有差距。

### 2.6 后端 D：契约测试、联调检查与数据库建模

负责范围：

- OpenAPI 契约检查
- 主流程测试清单
- 联调问题记录
- 回归检查
- 数据库方案设计和初始化

完成情况判断：**有成果，其中数据库草案相对最好，契约测试还需修正**。

已完成的内容：

- [server/app/tests/test_backend_b_contract.py](../../server/app/tests/test_backend_b_contract.py) 已经写出契约测试雏形，说明测试同学已经开始按主链路检查接口。
- [server/app/db/schema.sql](../../server/app/db/schema.sql) 已经提供了 MySQL 8.0 的表结构草案、索引、状态字段、初始化数据和种子数据。
- 数据库草案覆盖了用户、分类、商品、商品图片、订单、举报、收藏、刷新令牌、评价、管理员日志和统计表，覆盖面比较完整。

主要问题：

- 契约测试文件中预期的状态值和当前后端状态枚举存在不一致，例如测试里仍出现 `pending`、`reserved`、`confirmed` 这类小写值，而后端状态枚举是大写枚举值。
- 数据库 schema 虽然比较完整，但还需要继续对齐后端模型、OpenAPI 字段和实际代码中的状态语义。
- 第一阶段要求的“字段字段对齐、状态枚举对齐、分页参数对齐”还没有通过测试文件完全验证出来。

结论：后端 D 的数据库草案是当前一个比较扎实的产物，但测试契约还没完全和 OpenAPI/后端实现对齐。

## 3. 与 OpenAPI 的一致性判断

### 3.1 已经比较接近一致的部分

- 认证接口的基本路径已经对上：`/api/auth/wx-login`、`/api/auth/refresh`、`/api/auth/logout`、`/api/auth/me`。
- 用户基础接口已经对上：`/api/users/me`、`/api/users/me/favorites`、`/api/users/me/favorites/{productId}`。
- 商品和订单、举报和后台这些主路径已经在路由层出现，说明模块划分是按 OpenAPI 草案推进的。
- 统一响应结构方向正确，至少在后端 A 中已经体现为统一响应包装。

### 3.2 仍然存在明显偏差的部分

- 商品和订单模块大多还没有真正的数据驱动实现，因此虽然路径对上了，但字段语义不一定已经对上。
- 收藏列表接口当前返回的是收藏记录，不是商品详情对象，和 OpenAPI 对收藏列表的实际联调预期不完全一致。
- 前端展示层和后端状态枚举仍有命名差异，例如前端组件还在使用 available、reserved、sold 这一套旧状态语义，而后端统一状态枚举是 `DRAFT`、`PENDING`、`PUBLISHED`、`REMOVED`、`SOLD`。
- 契约测试文件中对状态值的断言也和当前后端枚举值不完全一致，需要统一。

## 4. 最关键的不符合项

下面这些问题是当前阶段最应该优先补的，因为它们会直接影响联调和验收：

1. 前端 A 的数据请求层没有完成。
   - [miniprogram/services/product.js](../../miniprogram/services/product.js) 仍是占位文件。
   - [miniprogram/utils/api.js](../../miniprogram/utils/api.js) 仍是占位文件。
   - 结果是首页和列表页虽然写了请求逻辑，但实际上拿不到真实接口数据。

2. 前端 B 仍然大量依赖 mock 数据。
   - 详情页没有接真实商品详情接口。
   - 个人中心页登录流程不是后端认证闭环。
   - 发布页没有接上传和提交接口。

3. 后端 B 的商品和订单主链路没有真正跑通。
   - 商品路由和订单路由里存在未定义 service 的调用。
   - 目前更多是“返回形状像接口”，而不是“接口背后有完整业务逻辑”。

4. 收藏列表接口语义与 OpenAPI 不一致。
   - 当前返回的是收藏记录和商品 ID。
   - OpenAPI 预期更接近“收藏商品列表”语义，前端联调时会受到影响。

5. 状态枚举在不同层之间没有完全统一。
   - 后端状态是统一的大写枚举。
   - 前端组件、部分测试和部分 mock 数据仍然使用旧语义或小写状态。

6. 契约测试还没有把 OpenAPI 的主链路完整覆盖到位。
   - 目前更像是有了测试模板，而不是完整、严格的主流程契约校验。

## 5. 已经做得比较好的部分

1. 认证与用户模块的方向是对的。
   - 至少已经把登录、刷新、当前用户、资料读取、收藏管理的接口入口搭出来了。

2. 数据库设计草案比较完整。
   - 核心实体、索引、状态字段和种子数据都有了。
   - 这为后续后端实现提供了比较好的落地基础。

3. 前端页面骨架已经齐了。
   - 首页、列表页、详情页、发布页、个人中心页都已经存在。
   - 这意味着 UI 层并不是从零开始。

4. 项目的分工边界和接口意图已经逐步明确。
   - 代码结构已经可以看出谁负责认证、谁负责商品、谁负责交易、谁负责举报、谁负责数据库和测试。

## 6. 当前状态对应到第一阶段目标的判断

### 6.1 已经部分实现的目标

- 微信登录与用户信息读取：后端 A 基本具备雏形。
- 商品列表、商品详情、商品发布的最小闭环：路由层和页面层都有雏形，但没有真正闭环。
- 举报提交和后台最基础管理接口：有接口入口，但业务还很薄。
- 统一接口返回结构：后端 A 已经做了统一响应包装，方向正确。

### 6.2 还未达标的目标

- 前端能看到真实数据：还没有达到。
- 后端能返回符合 OpenAPI 的字段：只有一部分接口接近，商品、订单、收藏语义仍有偏差。
- 测试能把主流程和失败路径先检查一遍：已有契约测试草案，但还没有形成完整可依赖的验收保障。

## 7. 建议的后续补全顺序

建议按下面顺序补，不要同时铺太多线：

1. 先补前端请求层。
   - 完成 [miniprogram/utils/api.js](../../miniprogram/utils/api.js) 和各个 `services/*.js`。
   - 先让首页、列表页、详情页、个人中心页能真正拿到接口数据。

2. 再补后端商品与订单主链路。
   - 先把商品列表、详情、发布做成真正的数据驱动接口。
   - 再把订单创建、详情、确认、完成、取消的状态流转补实。

3. 然后统一字段与状态枚举。
   - 前端展示状态、后端状态枚举、测试断言、数据库状态字段统一口径。

4. 最后收紧测试和文档。
   - 把契约测试补齐成功路径和失败路径。
   - 按 OpenAPI 重新核对收藏、举报、后台统计等接口返回值。

## 8. 后续推进建议

1. 前端 A 先补请求层，不要继续只改页面样式。
2. 前端 B 先把详情、个人中心、发布页从 mock 改成真实接口。
3. 后端 A 继续保留当前方向，但要把收藏列表和字段细节与 OpenAPI 再对齐一次。
4. 后端 B 先把商品和订单服务层落地，再谈页面联调。
5. 后端 C 先保证举报和统计接口的返回结构稳定，不要急着扩太多后台能力。
6. 后端 D 先把数据库和契约测试的状态值统一掉，再做下一轮联调检查。

## 9. 最终结论

当前仓库已经具备第一阶段开发的雏形，但还没有完成第一阶段验收要求。

如果按“能否联调、能否看到真实数据、能否符合 OpenAPI”来打分，当前状态更像是：

- 后端 A：接近完成。
- 前端 A：部分完成。
- 前端 B：部分完成。
- 后端 B：未完成。
- 后端 C：部分完成。
- 后端 D：有成果，但仍需对齐。

因此，后续补全工作的重点不应该再是“继续堆页面或继续加路由”，而是尽快把前端请求层、后端商品/订单业务层、OpenAPI 字段语义、状态枚举和测试断言统一起来，让主链路真正跑通。
