# 详细设计汇报信息汇总

本文档是面向开发组员和 AI Agent 的总览速查版，目标不是重新展开全部详细设计，而是把当前项目里已经明确的对象、状态机、职责边界、约束条件和主流程整理到一处，便于快速理解项目结构并减少口径不一致。

## 1. 文档使用方式

建议优先按下面顺序阅读：

1. 先看“对象总览”，知道项目里有哪些页面、组件、服务、接口和实体。
2. 再看“状态机总览”，避免状态值、状态流转和权限规则写错。
3. 然后看“职责边界”和“关键约束”，确保代码放对层、权限写对位置。
4. 最后看“主流程”和“给 Agent 的速查清单”，用于真正开始开发或生成代码。

如果实现代码与本文档有冲突，优先以 [docs/api/openapi.yaml](api/openapi.yaml)、[server/app/core/status.py](../server/app/core/status.py) 和 [server/app/db/schema.sql](../server/app/db/schema.sql) 为准。

## 3. 状态机总览

状态值是本项目最容易写乱的部分，因此这里单独列出。当前最重要的规则是：**状态值必须和后端枚举、OpenAPI、数据库字段保持一致，前端只负责显示层映射。**

### 3.1 用户状态机

| 项目 | 内容 |
| --- | --- |
| 状态值 | `ACTIVE`、`BANNED` |
| 含义 | `ACTIVE` 表示正常；`BANNED` 表示被管理员限制访问或使用平台能力。 |
| 作用范围 | 登录态、个人中心、后台用户管理、权限判断。 |
| 约束 | 普通用户不能自行修改状态；封禁/解封必须由管理员操作并留痕。 |

### 3.2 商品状态机

| 项目 | 内容 |
| --- | --- |
| 状态值 | `DRAFT`、`PENDING`、`PUBLISHED`、`REMOVED`、`SOLD` |
| 含义 | `DRAFT` 草稿；`PENDING` 待审核；`PUBLISHED` 已发布；`REMOVED` 已下架；`SOLD` 已售出。 |
| 作用范围 | 发布、编辑、审核、上下架、售出展示、商品详情和后台治理。 |
| 约束 | `SOLD` 后不允许随意改价或改状态；审核和交易流程都必须围绕该状态机展开。 |

### 3.3 订单状态机

| 项目 | 内容 |
| --- | --- |
| 状态值 | `CREATED`、`RESERVED`、`CONFIRMED`、`COMPLETED`、`CANCELLED` |
| 含义 | `CREATED` 初始创建；`RESERVED` 卖家确认/保留；`CONFIRMED` 买家确认收货；`COMPLETED` 完成终态；`CANCELLED` 取消终态。 |
| 作用范围 | 下单、确认、取消、完成、评价、超时释放。 |
| 约束 | 不能随意回退；不能重复完成或重复取消；必须先检查前置状态和权限。 |

### 3.4 举报状态机

| 项目 | 内容 |
| --- | --- |
| 状态值 | `OPEN`、`REJECTED`、`HANDLED` |
| 含义 | `OPEN` 待处理；`REJECTED` 被驳回；`HANDLED` 已处理。 |
| 作用范围 | 举报提交、后台处理、申诉和治理记录。 |
| 约束 | 处理结果要留痕，不能只停留在“提交成功”。 |

### 3.5 其他相关枚举

| 对象 | 说明 |
| --- | --- |
| `ReportTargetType` | `PRODUCT`、`USER`、`ORDER`。 |
| `ProductUpdateRequest.status` | 商品更新时允许写入的状态范围。 |
| `UserStatusPatchRequest.status` | 管理员修改用户状态时使用的枚举。 |

### 3.6 状态轮转机制明细

下面这部分补全的是“当前状态 -> 目标状态 -> 触发动作 -> 执行角色 -> 前置条件 -> 是否允许”的轮转规则，便于开发时直接对照实现，避免把状态机写成简单的字符串赋值。

#### 3.6.1 商品状态轮转表

| 当前状态 | 目标状态 | 触发动作 | 执行角色 | 前置条件 | 是否允许 |
| --- | --- | --- | --- | --- | --- |
| `DRAFT` | `PENDING` | 提交商品 | 卖家 | 标题、价格、分类、图片等必填项已通过校验 | 允许 |
| `PENDING` | `PUBLISHED` | 审核通过 | 管理员 | 商品已完成审核 | 允许 |
| `PENDING` | `REMOVED` | 审核驳回 / 撤回 | 管理员 / 卖家 | 商品尚未上架 | 允许 |
| `PUBLISHED` | `REMOVED` | 下架商品 | 卖家 / 管理员 | 商品当前已上架 | 允许 |
| `PUBLISHED` | `SOLD` | 交易完成 | 系统 | 关联订单已完成 | 允许 |
| `SOLD` | 任何状态 | 任何动作 | 任何角色 | 已进入终态 | 禁止 |
| `DRAFT` | `PUBLISHED` | 跳过审核直接上架 | 卖家 | 缺少审核通过记录 | 禁止 |

商品状态的关键约束是：`SOLD` 为终态，不能再改价、改状态或回退到 `PUBLISHED`；`REMOVED` 不应自动恢复为 `PUBLISHED`，若重新上架，应该走重新发布或重新审核流程。

#### 3.6.2 订单状态轮转表

| 当前状态 | 目标状态 | 触发动作 | 执行角色 | 前置条件 | 是否允许 |
| --- | --- | --- | --- | --- | --- |
| `CREATED` | `RESERVED` | 卖家确认 | 卖家 | 订单未被取消 | 允许 |
| `CREATED` | `CANCELLED` | 取消订单 | 买家 / 卖家 | 无 | 允许 |
| `RESERVED` | `CONFIRMED` | 买家确认收货 | 买家 | 卖家已确认 | 允许 |
| `RESERVED` | `CANCELLED` | 取消订单 | 买家 / 卖家 | 未确认收货 | 允许 |
| `CONFIRMED` | `COMPLETED` | 完成订单 | 系统 / 双方 | 买家已确认 | 允许 |
| `CONFIRMED` | `CANCELLED` | 取消订单 | 买家 / 卖家 | 无 | 禁止 |
| `COMPLETED` | 任何状态 | 任何动作 | 任何角色 | 已进入终态 | 禁止 |

订单状态的关键约束是：`CREATED -> RESERVED -> CONFIRMED -> COMPLETED` 是主链路，`CANCELLED` 是终态；`COMPLETED` 不可再取消，`CONFIRMED` 之后的取消要被严格禁止，并且所有重复调用都应被视为幂等或冲突处理，而不是重新写入新状态。

#### 3.6.3 举报状态轮转表

| 当前状态 | 目标状态 | 触发动作 | 执行角色 | 前置条件 | 是否允许 |
| --- | --- | --- | --- | --- | --- |
| `OPEN` | `HANDLED` | 完成处理 | 管理员 | 已完成核查并记录处理结果 | 允许 |
| `OPEN` | `REJECTED` | 驳回举报 | 管理员 | 举报证据不足或不成立 | 允许 |
| `REJECTED` | 任何状态 | 任何动作 | 任何角色 | 已进入终态 | 禁止 |
| `HANDLED` | 任何状态 | 任何动作 | 任何角色 | 已进入终态 | 禁止 |
| `OPEN` | `OPEN` | 重复提交处理结果 | 管理员 | 状态未变化 | 禁止 |

举报状态的关键约束是：处理后必须记录结果、处理人和理由；如果需要复核，应该通过申诉或新记录进行，而不是把 `REJECTED` / `HANDLED` 直接改回 `OPEN`。

#### 3.6.4 用户状态轮转表

| 当前状态 | 目标状态 | 触发动作 | 执行角色 | 前置条件 | 是否允许 |
| --- | --- | --- | --- | --- | --- |
| `ACTIVE` | `BANNED` | 封禁用户 | 管理员 | 存在违规记录或治理依据 | 允许 |
| `BANNED` | `ACTIVE` | 解封用户 | 管理员 | 封禁原因已解除 | 允许 |
| `ACTIVE` | `ACTIVE` | 重复提交封禁 | 管理员 | 状态未变化 | 禁止 |
| `BANNED` | `BANNED` | 重复提交解封 | 管理员 | 状态未变化 | 禁止 |

用户状态的关键约束是：普通用户不能直接修改自己的状态；管理员的封禁与解封都应进入审计记录，并且恢复到 `ACTIVE` 时要明确保留操作理由。

## 4. 职责边界

### 4.1 前端职责边界

1. 页面对象负责展示和轻交互，不直接绕过 service 操作数据。
2. 组件对象只做复用展示，不写完整业务流程。
3. 前端服务对象统一封装请求，页面不要到处直接写请求细节。
4. 工具对象统一管理请求、存储、校验和格式化。

### 4.2 后端职责边界

1. 路由层只接收参数、调用 service、返回结果，不写复杂业务逻辑。
2. service 层负责业务规则、权限校验、状态机和幂等控制。
3. crud 层只负责数据库读写，不负责流程编排。
4. models 和 schemas 负责结构定义，不负责业务判断。

### 4.3 管理员与普通用户边界

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 普通用户 | 浏览商品、发布自己的商品、发起订单、收藏、举报、提交申诉。 | 不能替别人改资料、封禁用户、处理举报、直接发布成已上架状态。 |
| 卖家 | 操作自己发布的商品、确认相关订单、处理与自己相关的交易。 | 不能越权处理他人商品、他人订单和后台治理动作。 |
| 管理员 | 审核商品、处理举报、封禁用户、查看统计、读取日志。 | 不能无痕操作，所有治理动作都应留痕。 |

## 5. 关键约束条件

### 5.1 数据归属

| 字段/对象 | 规则 |
| --- | --- |
| 用户资料 | 用户资料由用户或管理员在权限范围内维护。 |
| 商品价格 | 发布后允许修改，但一旦出现订单或进入特定终态，就需要锁定或严格限制。 |
| 订单金额 | 下单后应锁定，不允许后续随意变化。 |
| 举报处理结果 | 处理后不允许随意重写，若需复核应走新流程。 |

### 5.2 接口契约

1. 基础路径统一为 `/api`。
2. 需要鉴权的接口统一走 Bearer JWT。
3. 列表接口统一支持 `page`、`size`，并在需要时支持 `keyword`、`sort`、`categoryId`。
4. 时间字段统一使用 ISO 8601。
5. 错误返回需要尽量保持统一响应结构，避免前端同时处理多种错误格式。

### 5.3 幂等和重复提交

以下行为都要提前定义重复提交策略：

1. 收藏同一个商品。
2. 重复提交订单。
3. 重复提交举报。
4. 重复审核同一商品。
5. 重复完成同一个订单。

原则是：要么幂等返回成功，要么明确返回错误，不允许制造重复脏数据。

### 5.4 错误处理

必须统一以下失败场景：

1. 登录失败。
2. 权限不足。
3. 资源不存在。
4. 状态不允许。
5. 重复提交。

建议在后端 `exceptions.py` 里集中定义少量基础异常类，再由路由层交给统一异常处理器转换成标准响应。

## 6. 主流程对象协作

### 6.1 登录与注册

1. 小程序获取微信 code。
2. 前端 `auth.js` 发起登录请求。
3. 后端 `auth_service` 完成 token 签发和用户识别。
4. 返回 `AuthTokens` 和 `UserProfile`。

### 6.2 浏览与搜索

1. 首页或列表页触发商品查询。
2. 前端 `product.js` 调用商品列表接口。
3. 后端 `product_service` 根据筛选条件读取商品。
4. 页面渲染列表、空状态或错误提示。

### 6.3 发布与审核

1. 用户在发布页提交商品信息。
2. 前端 `product.js` 发起发布请求。
3. 后端 `product_service` 创建商品并进入待审核或草稿流程。
4. 管理员通过 `admin_service` 审核并变更状态。

### 6.4 下单与交易

1. 买家在详情页发起交易。
2. 前端 `order.js` 调用下单接口。
3. 后端 `order_service` 检查商品是否可售、是否已有活动订单。
4. 卖家确认、买家确认、完成订单，并联动商品状态变更。

### 6.5 举报与处理

1. 用户在详情页或相关页面提交举报。
2. 前端 `report.js` 调用举报接口。
3. 后端 `report_service` 记录举报并进入待处理状态。
4. 管理员处理举报、记录动作并根据结果更新状态。

## 7. 调用顺序

推荐的调用链路是：

1. 页面对象触发交互。
2. 前端 service 对象发请求。
3. 后端 router 接收请求并解析参数。
4. 后端 service 做业务校验和流程推进。
5. crud 负责持久化。
6. model 和 schema 负责结构约束。

## 8. 给开发者和 AI Agent 的速查清单

### 8.1 开发时先确认

1. 这个功能属于页面、组件、服务、路由、业务、数据库还是测试层。
2. 它对应的状态机是哪一个。
3. 谁拥有这个数据的修改权。
4. 这个接口是否需要鉴权。
5. 重复提交时应该幂等还是报错。

### 8.2 生成代码前先检查

1. 状态值是否与 `status.py` 一致。
2. 请求体和返回体是否与 OpenAPI 一致。
3. 路由里是否避免直接写复杂业务逻辑。
4. service 是否已经包含权限和状态校验。
5. 前端展示层是否只是做映射，而不是自己再发明一套状态。

### 8.3 最容易出错的点

1. 商品和订单状态值大小写不一致。
2. 前端和后端对字段名理解不同。
3. 路由层写了过多业务逻辑。
4. 重复提交没有做幂等控制。
5. 权限边界没有提前定清楚。

## 9. 推荐后续继续展开的内容

如果要继续往答辩或详细设计里补，建议优先展开以下几部分：

1. 登录、发布、下单、举报四条主流程的对象交互图。
2. 每个 service 的职责边界和调用顺序。
3. 每个状态机的允许流转、禁止流转和权限要求。
4. 页面对象到 service 对象的映射关系。
5. 管理员能力与普通用户能力的边界说明。

## 11. 开发入口卡：第一次接任务时先看什么

这一部分是给第一次接到任务的人和 Agent 用的“起步导航”。目标不是替代需求说明，而是让人能在 5 分钟内知道自己该改哪一层、先看哪几个文件、怎样判断做完没有。

### 11.1 任务先分层

收到任务后，先判断它属于哪一层：

1. 页面层：只改 `pages/*`，处理页面展示、交互和少量本地状态。
2. 组件层：只改 `components/*`，处理可复用展示和轻交互。
3. 前端服务层：只改 `services/*` 和 `utils/api.js`，处理接口封装、请求参数和统一错误处理。
4. 后端路由层：只改 `server/app/api/routers/*`，负责收参和返回，不写复杂业务。
5. 后端业务层：只改 `server/app/services/*`，处理状态机、权限、幂等和流程推进。
6. 数据层：只改 `server/app/models/*`、`server/app/crud/*`、`server/app/db/*`，处理数据结构、读写和初始化。
7. 契约与测试层：只改 `docs/api/openapi.yaml`、`server/app/tests/*`、`docs/testing/*`。

### 11.2 功能任务卡模板

每个新功能最好先填下面这张卡，再开始写代码：

| 项目 | 需要确认的内容 |
| --- | --- |
| 任务归属 | 这个功能属于商品、订单、举报、用户还是后台。 |
| 所属层级 | 页面、组件、服务、路由、业务、数据还是测试。 |
| 输入 | 请求参数、表单字段、路径参数、Query 参数。 |
| 输出 | 返回字段、列表结构、错误码、状态变化。 |
| 权限 | 公开、已登录、卖家、买家、管理员。 |
| 状态机 | 需要操作哪个状态值，是否有前置状态。 |
| 幂等 | 重复点击时应成功、报错还是忽略。 |
| 验收 | OpenAPI 是否对齐、状态是否对齐、测试是否能过。 |

### 11.3 常见任务到文件的快速映射

| 任务类型 | 优先修改位置 |
| --- | --- |
| 登录与 token | `server/app/api/routers/auth.py`、`server/app/services/auth_service.py`、`miniprogram/services/auth.js`、`miniprogram/utils/storage.js` |

| 发布商品 | `server/app/api/routers/products.py`、`server/app/services/product_service.py`、`miniprogram/pages/post`、`miniprogram/services/product.js` |

## 12. 主流程执行手册：拿到任务后怎么落地

这一部分把“知道要做什么”进一步变成“按照什么顺序做”，适合开发者和 AI Agent 直接照着执行。

### 12.1 通用执行顺序

1. 先看 OpenAPI，确认接口路径、请求体、响应体、枚举值和分页约束。
2. 再看本汇总文档，确认对象、状态机、职责边界和禁止路径。
3. 再看当前代码，确认已有路由、service、schema、页面或组件是否已经存在。
4. 决定改动落点，优先改最内层的业务/数据实现，再改路由，最后改前端展示。
5. 补测试或契约清单，确保成功路径和失败路径都能说明白。
6. 最后回头检查状态值、返回结构、权限判断和幂等策略有没有对齐。

### 12.2 主流程最小检查清单

#### 登录与用户

1. 输入是不是 `code` 或 `refreshToken`。
2. 返回是不是 `AuthTokens` 或 `UserProfile`。
3. 是否需要 `Bearer`。
4. 失败时是否仍然保留统一响应结构。

#### 商品

1. 列表是否支持分页和筛选。
2. 详情是否能按 `productId` 查到完整对象。
3. 发布是否会进入正确状态。
4. 下架、删除、售出是否会触发正确状态机。
5. 上传图片是否回填 URL 或文件引用。

#### 订单

1. 下单前商品是否处于可售状态。
2. 订单是否生成正确的状态。
3. 卖家确认、买家确认、完成、取消是否遵守顺序。
4. 重复操作是否幂等或被拒绝。
5. 完成订单后商品是否联动到 `SOLD`。

#### 举报与后台

1. 举报是否能记录目标类型、目标 ID 和原因。
2. 处理动作是否能记录结果和理由。
3. 用户封禁/解封是否有权限校验和审计记录。
4. 统计和日志是否返回稳定字段。

### 12.3 任务完成标准

一个功能通常算“完成”，至少要满足下面 5 条：

1. OpenAPI 路径、字段和枚举不再冲突。
2. 相关状态机轮转规则已经写进 service 或等价层。
3. 需要鉴权的地方已经做了鉴权。
4. 重复提交和非法状态有明确处理。
5. 文档、测试和代码对得上。

## 13. 目录规范：开发者和 Agent 到底应该往哪里写

这一节直接把“写哪里”说清楚。目的是避免 AI Agent 或新成员把功能代码写到错误层级，导致后续返工。

### 13.1 前端目录规范

建议前端以 `miniprogram/` 作为工程根目录：

```text
miniprogram/
	app.js
	app.json
	app.wxss
	pages/
		home/
		list/
		detail/
		post/
		user/
		admin/
	components/
		item-card/
		search-bar/
		empty-state/
		loading-state/
		error-tip/
		confirm-dialog/
	services/
		auth.js
		user.js
		product.js
		order.js
		report.js
		admin.js
	utils/
		api.js
		storage.js
		validator.js
		formatter.js
		constants.js
	assets/
		images/
		icons/
	styles/
		common.wxss
		variables.wxss
```

前端写作规则：

1. 页面层只放页面入口和页面状态，别把复杂请求逻辑散在页面里。
2. 组件层只做可复用展示，不要写完整业务流程。
3. 所有请求先走 `utils/api.js`，再由 `services/*` 按模块封装。
4. `utils/storage.js` 统一管理 token 和用户信息，不要每页自己写一套。
5. 状态文案、颜色、空状态尽量统一映射，不要每页各写一套。

### 13.2 后端目录规范

建议后端以 `server/app/` 为核心：

```text
server/app/
	main.py
	api/
		routers/
		deps/
	core/
		response.py
		config.py
		status.py
		exceptions.py
		security.py
	schemas/
	models/
	crud/
	services/
	db/
	utils/
	tests/
```

后端写作规则：

1. 路由层只收参、调用 service、回结果。
2. service 层处理状态机、权限和幂等。
3. crud 层只负责数据库读写，不编排流程。
4. `status.py` 集中维护状态枚举，别把字符串散落在各文件里。
5. schema 先于 model 设计时保持和 OpenAPI 对齐。

### 13.3 任务类型与目录对应表

| 任务类型 | 主要写入目录 | 说明 |
| --- | --- | --- |
| 页面样式/交互 | `miniprogram/pages/*` | 只做页面行为，不碰后端业务实现。 |
| 可复用 UI | `miniprogram/components/*` | 用于卡片、弹窗、空状态、加载态。 |
| 请求封装 | `miniprogram/services/*`、`miniprogram/utils/api.js` | 不要把请求散在页面里。 |
| 登录态/缓存 | `miniprogram/utils/storage.js` | 统一 token 和用户信息管理。 |
| 路由入口 | `server/app/api/routers/*` | 参数解析和响应出口。 |
| 业务规则 | `server/app/services/*` | 状态机、权限、幂等、流程推进。 |
| 数据结构 | `server/app/schemas/*`、`server/app/models/*` | 请求体、返回体、ORM 定义。 |
| 数据读写 | `server/app/crud/*`、`server/app/db/*` | 查询、更新、初始化、种子数据。 |
| 契约/测试 | `docs/api/openapi.yaml`、`server/app/tests/*`、`docs/testing/*` | 记录接口约定、测试用例和问题。 |

### 13.4 最容易放错的东西

1. 把复杂业务写进路由层。
2. 把请求封装写进页面里。
3. 把状态值散落在前端和后端各个角落。
4. 把数据读写和业务判断混在一起。
5. 把测试、契约和实现口径写成三套。

### 13.5 给 Agent 的最短指令

当 AI Agent 接到任务时，最有效的约束写法通常是：

1. 先指出任务属于哪个模块和哪一层。
2. 明确要改的文件目录。
3. 明确要遵守的状态机和权限。
4. 明确 OpenAPI 哪些字段不能变。
5. 明确完成标准是接口对齐、状态对齐还是页面可用。

## 14. 目录规范与状态机的组合使用建议

如果要把本文档真正用起来，建议按“目录规范先定位置，状态机先定行为，OpenAPI 再定字段”的顺序做事：

1. 先通过目录规范判断代码应该写到哪里。
2. 再通过状态机判断这段逻辑允许怎么流转。
3. 再通过 OpenAPI 判断请求和返回应该长什么样。
4. 最后通过测试或 QA 文档判断这个功能是否真的可验收。

这样做的好处是，开发者和 AI Agent 都不会只看到“怎么写代码”，而是能同时看到“写到哪里、为什么这么写、写完怎么验收”。
