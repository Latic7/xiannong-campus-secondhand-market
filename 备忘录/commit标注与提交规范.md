# Git + VSCode 新手完整极简总结（命令行 + 可视化双版本）
**main 主分支 + 开发分支** 开源规范协作

## 一、核心规则
1. 主分支 `main` 永远只存稳定可用代码，**不在 main 直接改代码**
2. 所有开发、改动全在自己的分支做
3. 日常只做：拉取→写代码→规范提交→推送
4. 功能**完整做完、自测没问题**，才提 PR 合并到 main
5. Commit 要规范，此处参考 0.commit标注简单规范（文件最开头）

---

## 二、分支创建（两种方式）
### 1. 命令行
```bash
# 拉取最新
git pull
# 创建并切换到新分支 
git checkout -b 自己的分支名
# 推送到远程 GitHub
git push origin 自己的分支名
```

### 2. VSCode 可视化
1. 左下角点分支名 → 创建新分支
2. 输入 `自己的分支名` → 自动切换到该分支
3. 源代码管理点 **发布分支**，同步到云端

---

## 三、每日固定工作流程（两种方式）
### 方式A：命令行每日操作
```bash
# 1. 切到开发分支
git checkout 自己的分支名
# 2. 拉取远程最新代码
git pull
# 3. 改完代码后，暂存所有更改
git add .
# 4. 规范提交
git commit -m "feat: 新增xx功能"
# 5. 推送到 GitHub
git push
```

### 方式B：VSCode 可视化每日操作
1. 左下角确认在 **自己的分支名** 分支
2. 点**拉取**（同步云端最新）
3. 正常写代码、改代码
4. 左侧「源代码管理」：
   - 自动识别改动文件
   - 输入**规范 Commit 备注**
   - 点**提交**
5. 点**推送**，上传到 GitHub

---

## 四、三个按钮通俗定义
1. **抓取**：只下载远程更新，不合并、不改本地代码，纯查看
2. **拉取**：下载 + 自动合并远程最新代码，每天开工必点
3. **推送**：把本地已提交的规范代码，上传到 GitHub

---

## 五、Commit 规范
固定格式：`类型: 简短描述`
常用类型：
- `feat:` 新增功能
- `fix:` 修复 Bug
- `refactor:` 代码优化重构
- `docs:` 文档/注释修改

示例：
```
feat: 新增ccs编辑模块
fix: 修复列表加载异常
refactor: 优化接口请求逻辑
```

---

## 六、PR 提交时机
1. 自己分支功能**全部开发完成**
2. 本地自测无明显报错、不破坏原有逻辑
3. 清理调试代码、无用注释后
4. 再去 GitHub 网页端提交 PR，等待合并

---

## 七、开源开发者底线
1. 不在主分支瞎改代码
2. 提交前简单自测，不扔明显报错代码
3. 清理调试垃圾代码再提交
4. Commit 严格规范，不糊弄、不给维护者添负担
5. 半成品绝不合入主分支
